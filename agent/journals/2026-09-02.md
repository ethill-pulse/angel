## prek hook install scope (verified)
`.githooks/pre-commit install` is fleet-repo-only. `prek install` has no global flag (only
`--git-dir`), the wrapper derives FLEET_HOME from its own path and rewrites only
`$FLEET_HOME/.git/hooks/*`, and global `core.hooksPath` / `init.templateDir` are both unset and
untouched by the flow. Only user-level artifact is `$PREK_HOME` (hook env cache + prek.log).

**Gotcha**: the wrapper does NOT `cd` to `$FLEET_HOME` before calling `prek install` — it inherits
cwd. Run it from inside another repo and prek installs shims into THAT repo while the sed loop
rewrites fleet's hooks. Always run from the fleet root.

## Recon agent returned — PR 2 findings (recorded as §13 of the design doc)
Biggest items:
- **DO NOT reuse `CommonRecordType.BENCHMARK_RATES`.** Beyond watermark clobbering between the two
  jobs, `MarketDataProcessingRecordHandlerImpl:37` gates EOD TRADE processing on
  `{SECURITY_PRICES_EOD, FX_RATES, BENCHMARK_RATES}`. The digital job writing that record would
  falsely tell Voyager the FACT load finished, releasing EOD early against stale rates — corrupting
  equity swaps, not just our job. Needs its own enum constant. New Q14: does
  `processing_record.record_type` have a DB CHECK constraint to widen?
- **Simplification: reuse the existing `snowflake-datasource` profile** (as `load-corporate-actions-job`
  does) instead of building a `digital-datasource`. Its URL has no `db=` param, so queries are fully
  DB.SCHEMA.OBJECT-qualified. Avoids 3 env YAML edits, a new profile YAML, a new config class, and an
  @Import change. PR 2 is meaningfully smaller than I'd scoped.
- **New external red tape (Q15): Vault + jetty.** `spring.application.name` doubles as the Vault key,
  so a new job needs `svc-swaps-load-digital-rates-job-pk` static creds, a
  `{env}/voyager/swaps-load-digital-rates-job` secret path, and a k8s auth role — all in jetty.
  `spring.cloud.vault.fail-fast: true` → missing path is a hard startup failure. Should be filed
  alongside the Snowflake ticket since it's the same critical path.
- **New D7: cron minute offset.** Both jobs have `spring.flyway.enabled: true` and would race on
  Postgres migration at an identical cron minute. Keep 17:00 ET, offset the minute (e.g. `5 17 * * *`).
  Eric's "not changing 0 17" decision was about the hour; this is compatible.
- Flyway definition seeding is mandatory or the job is a green no-op (getBenchmarksForSystem filters
  system + deleted=false, then isActive()). Next version V0.1.37.
- `settings.gradle` omission = total silent failure. `container-images.lst` + `services_filter.yml`
  are GENERATED — run `./gradlew init`, don't hand-edit. `deploy/deploy.py` must exist or no image is
  built, and its "auto-generated DO NOT MODIFY" header is stale/wrong.

## Business/economics decisions on the perp funding rate (Eric's questions, no code)
**Q: net against OBFR, or just the instrument's funding?** → They're ADDITIVE, not substitutes.
Perp funding is a peer-to-peer transfer tethering perp to index (zero-sum, one rate per instrument
per interval, sign says direction). Cash financing (OBFR ± spread) is the cost of the money and
exists regardless. Client owes both. Blend = `OBFR + annualized_funding`, spread stays free as CS
margin. Verified against both legs: OBFR 5%, funding +10%, spread 1% → long pays 16% (15+1), short
receives 14% (15-1). With funding -10% → blend -5%, long RECEIVES 4%, short PAYS 6%. Blend works and
the spread lands as house margin on both sides.
**All-in rates can legitimately go NEGATIVE** (funding more negative than OBFR). Must survive end to
end — flagged as a test case since negative rates are where sign bugs hide.

**Q: publish separate long and short rates?** → NO, one rate. Funding is a single market observable;
the long/short flip is a property of the POSITION, not the data. Two rates would be redundant, would
create an "always exact negatives" invariant that breaks silently on a partial write, and would move
position-side logic into the market-data feed.

**CONVENTION TO PIN DOWN (the contract):** *a positive published rate is a cost to the long and a
benefit to the short.* Binance is long-pays-on-positive and Voyager's benchmark is long-pays-on-
positive (long = benchmark + spread, short = benchmark − spread), so the orientations already agree
and NO sign flip is needed anywhere. This is the thing a future implementer would invert.

**Multi-venue sign risk:** pulse has Binance/Bybit/OKX/BitMEX. Venue funding-sign conventions are not
guaranteed to agree (some frame it as what shorts receive; inverse-settled contracts can invert).
Normalize sign at the VENUE ADAPTER where the convention is known, and test per venue — otherwise you
get a rate correct for 3 venues and inverted for the 4th, surfacing only as unexplained P&L on a
subset of positions.

**Units chain confirmed:** Binance `0.00005000` is a decimal fraction for the 8h interval (=0.005%).
Annualized: × intervals/day × day-count. 0.00005 × 3 × 365 = 0.05475 = 5.475%. Then RATE_VALUE must
be PERCENT (loader does pctToRate ÷100) → 5.4750. Two unit conversions back to back; each is a 100x
or 1095x silent error.

**⚠ CORRECTION TO THE DESIGN DOC (§7.1/§11.3):** I wrote the annualization as ×365. That is
UNVERIFIED. Voyager divides by a PER-CURRENCY dayCount from reference data (`currency.getDayCount()`,
360 or 365) and USD money-market convention is frequently 360. If Voyager holds 360 for USD and we
annualize at 365, every charge is off by 365/360 ≈ 1.4% — small enough to pass eyeballing, large
enough to matter. MUST confirm USD's dayCount value and annualize on the same basis.

**Don't hardcode 3 intervals/day.** Binance moves symbols to 4h (or shorter) during high volatility;
`fundingIntervalHours` / `nextFundingTime` expose it. Hardcoding 3 understates by half on a 4h day.
Also: with mixed interval lengths in one day, weight by interval duration rather than a flat mean.

**Basket note:** multi-instrument baskets need NOTIONAL-WEIGHTED blending, not averaging, and the
weights move with prices so the weighting date is a convention to pin. Keep intra-day interval
aggregation and cross-instrument blending as distinct steps.

## Day-count reframe: for FUNDING the divisor cancels; for OBFR it doesn't
Refining the ×360 vs ×365 risk from earlier — it's less scary than I framed it, but the fix is
different from what I said.

Perp funding has NO day-count convention. It isn't an annualized rate; it's a realized per-interval
payment ("0.005% of notional, now"). No year fraction, no accrual basis. Annualizing it is something
WE invent to fit Voyager's framework. So the divisor cancels:
    annualize:  funding_per_interval × intervals_per_day × D
    Voyager:                                             ÷ D
    net:        funding_per_interval × intervals_per_day        (D gone)
=> ANY D is fine for the funding component provided both sides use the SAME one. The ~1.4% risk is
purely a MISMATCH error, not a convention error.

BUT D is not free for the OBFR component. OBFR is genuinely quoted Actual/360 (USD/EUR money markets:
SOFR, EFFR, OBFR, repo, CP, €STR, EURIBOR; whereas GBP/SONIA, AUD, NZD, HKD, SGD, ZAR use Act/365F —
which is exactly why Voyager reads dayCount PER CURRENCY rather than as a constant). Accruing OBFR on
365 misstates the cash financing leg for real.

**Resolution: defer, don't choose.** Read Voyager's existing USD dayCount and annualize funding to
match it. Whatever it holds is presumably already correct since OBFR/SOFR equity swaps are the
existing business — if it were wrong, every USD swap on the book would already be mis-accruing. If it
turns out to be 365 for USD, that's a pre-existing question about the equity swap book, NOT something
to fix in this PR.

Reference: Act/360 over a real year yields 365/360 = 1.01389 of the quoted rate, so 5% Act/360 earns
5.069% — that factor IS the 1.4%.
