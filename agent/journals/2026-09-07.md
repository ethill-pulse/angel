
## refdata-fetcher stuck with no venues

Eric reported refdata-fetcher occasionally starting with zero venue integrations, then failing
every fetch forever: `failed to fetch BYBT - Exception { message: "Unable to find ByBit" }` for
every venue, every cycle. Restarted it in clearstreet-dev with kubectl first (his AWS SSO token
had expired, needed `aws sso login --sso-session digital`), which cleared it but destroyed the
failing pod's logs before we knew we wanted them.

Eric's hypothesis was right and sharper than mine: conductor republishes venue definitions to a
Kafka topic, refdata-fetcher's recovery may snapshot the topic before conductor's flush lands, and
**venue integrations are built once at startup rather than lazily** — so an empty recovery latches
forever. Confirmed: `VenueIntegrationManager::new` clones `refdata_cache.map_venues(..)` into a
`HashMap` that is never rebuilt, while the background consumers keep feeding the cache. One side is
a frozen snapshot, the other a live view — which is exactly why the fetcher still iterates every
venue code while every factory lookup fails.

Only opens when venue config actually changed, since `migrate_configured_venue` produces nothing
when definitions are unchanged. Hence "occasionally".

Fix: lazy repair on miss in `get_factory` — Eric chose this over a periodic reconcile, and warn
over failing startup, on the reasoning that a self-healing registry makes an empty initial set
transient rather than fatal. Branch `et.refdata_factory_repair`, 49 tests green, lint clean.

Not fixed: `check_recovery` still treats an empty topic as successful recovery. Deterministic, not
a race — a fresh environment would come up permanently venue-less.

Also learned the branch convention is `et.<snake_case>`, and that repo tooling rewrites commit
messages and creates the convention-named branch itself — my "Deribit Subscribe Pacing" commit
became `dbt better pacing on subscription` on `et.dbt_better_pacing`, duplicating a branch I had
made by hand.

Four older branches exist on the same Deribit throttling problem (et.throttle_dbt_subscribe,
et.dbt_incremental_throttle, et.dbt_subscription_splitting, et.deribit_sub_fix) — this weekend's
change is iteration five. Flagged to Eric; their diffs vs main are too age-polluted to tell
cheaply whether any hold unmerged work.
