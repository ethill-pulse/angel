## 15:52
Eric added a requirement: don't miss final rates — poll REST at startup and publish the last
final result, "we are doing this with binance IIRC". He's right, and the Binance precedent is
exact: BinanceFundingRatePoller (venues-binance/src/integration/mktdata/rest/funding_rate.rs).

The mechanic is a per-symbol `last_published` watermark. Unwatermarked symbol (= startup) →
publish only the LATEST settlement to seed downstream; thereafter only settlements past the
watermark. Empty history leaves the symbol unwatermarked so the next poll retries. Registered in
create_mktdata_receiver as MultiServiceWorkerChain{chain: vec![ws, rest]} when feed_type ==
MarkPrice, gated by a `poll_final_funding_rate` venue kvp. That gate's doc comment states the
same split we hit: "Settled funding rates only exist over REST; the WS markPrice stream is
theoretical."

This probably kills the WS-post fundingHistory leg I'd designed. A watermarked REST poller covers
BOTH the startup seed AND every ongoing hourly settlement with gap recovery, so WS-post is
redundant — and keeping both means two independent producers of Final entries for the same symbol
with no shared watermark. Since `ts` (funding timestamp) is explicitly the downstream idempotency
key (comment in funding_rate_record_to_mark_price), duplicate Finals from two transports is a
real correctness bug, not cosmetic. Latency is no argument either — funding settles hourly.
Sent that to the design agent as a recommendation to verify or overturn, not a decree.

HYPL frictions I flagged for the design: fundingHistory is a POST with a JSON body (Binance's
throttler builds GET URLs — may not carry a body at all); startTime is REQUIRED on HYPL's call
unlike Binance's limit-only; and HYPL's existing REST mktdata uses the async http client while
Binance's poller uses the non-blocking one.

Lesson worth keeping: I went to WS-only because the docs showed WS could technically fetch
fundingHistory. Eric's instinct — seed from REST at startup regardless — is about not missing
data across restarts, which no amount of WS capability solves on its own.

## 16:20
Design came back. Verified every load-bearing claim myself against the code rather than trusting
the report — all held, one was better than assumed.

Final design: two legs split by transport, one producer per settl_price_type.
- Theoretical <- WS activeAssetCtx (markPx -> MarkPrice, oraclePx -> IndexPrice, funding ->
  FundingRate+Theoretical). Spot ctx has no funding/oraclePx, so spot emits markPx only —
  modeled as two schema messages so a spot frame structurally CANNOT decode as the perp type.
- Final <- REST poller, Binance shape, watermarked. WS-post leg dropped entirely.

The decisive argument against WS-post wasn't the one I expected. venues-internal's
merge_mark_price (mktdata/throttle.rs:~180) merges conflated MarkPrice entries keyed on
entry.r#type ALONE. So a Final FundingRate entry and a Theoretical FundingRate entry in the same
throttled chain silently overwrite each other. Verified this myself. The REST poller chain
(MutServiceChain -> FeedEventVecPopulator -> rb_producer -> IdleWorkerStatusService) has no
MarkPriceThrottleService, while the WS chain does (ws/mod.rs:180,306,458) — so the transport
split is what makes it correct, not just tidy. Keeping Final on WS would have needed a
venues-internal merge-key change.

Also verified: MockHttpClient already implements post AND already captures request bodies via
enable_request_logging()/request_store — so the design's open question about extending the mock
is closed, no extension needed.

Notable deviation from the Binance precedent, and I agree with it: NO kvp gate. Binance hides its
poller behind poll_final_funding_rate (default false) for staged rollout. For HYPL a false/missing
kvp reproduces exactly the silent data loss this work exists to prevent, since
clearstreet-lastprice-publisher republishes ONLY Final funding entries. Feed-type enablement is
already the control point. Means no venues/*.yml changes at all.

startTime is required on HYPL's fundingHistory (Binance gets by with limit alone), and the
throttler's construct fn is a plain fn pointer that can't capture poller state — so the request
window is a fixed 24h lookback and the watermark does the dedup. >24h outage loses intermediate
settlements but still re-seeds the latest. Same tradeoff Binance accepts beyond limit=10.

Split into 3 agents: (A) venues-internal throttler send_post_requests — it's GET-only today,
confirmed; (B) HYPL schema + venue.rs helpers + WS Theoretical leg; then (C) REST poller +
factory unlock, which depends on both. A and B running in parallel now.

Told Eric about the one reversal — he'd said "prioritize websocket if available" and this ends up

**What the doc describes**: tokenised *NMS equities* (not crypto-native assets) trading on an exchange-operated ATS, RFQ-style ("RFR"), settling atomically on a permissioned chain Clear Street operates every validator of. Cash leg is USDC. SD=TD, gross, pre-funded, no netting, no credit. Books remain record of ownership. **Key findings I surfaced** (full list in the response):
- Direct internal contradiction: page 04 says designated-wallet *balance is the buying power*; page 09 says balance shows full holding with elected quantity frozen inside it. Venue would let a holder sell frozen stock.
- Failure list "insufficient funds or unknown symbol" is incomplete — whitelist rejection, chill, pause, freeze, gas exhaustion all exist per their own pages.
- USDC settled at one rate/day, possibly a 90-day MA. Standing arbitrage vs market USDC; worst exactly during a depeg. No depeg playbook, no cash-leg analogue to a depository chill.
- No short selling / locate / borrow anywhere. With gross pre-funding, no netting, and N sleeves per underlying, a two-sided MM has to pre-position every sleeve. Probably fatal for LP economics — biggest omission.
- Omnibus "undecided" is a go/no-go not a detail; doc itself says liquidity depends on it.
- Overnight: LPs asked to quote inside NBBO when SIP is down, with no book/quotes published and last-print publication "undecided".

- Doc never states the benefit that justifies the long "what the chain cannot do" list — every claimed property is a property of a transactional DB given one operator, no external nodes, no fee market, no composability.

**Pulse-side conflicts**:
- Instrument identity: FIX tag 48 carries composite (underlying + source) token id, format explicitly unfixed. Pulse's refdata keys instruments on normalized `symbol` + `(venue, venue_symbol)` + `base_asset`/`quote_asset`; positions/margin aggregate by asset code. No sleeve/source dimension exists. Sleeves would either wrongly net or fragment asset codes.
- `messages-public/schemas/settlement.yml` `clearstreet_settlement_event` carries a required T+n `settlement_date` round-tripped from what Pulse sent CS at trade creation; new model has no settlement date and is venue-initiated. - No timeout on settlement response by design; Pulse's flow layer is request/response with correlation+timeouts. Pending match with no terminal state = inventory an LP can't re-quote.
