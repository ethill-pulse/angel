## ~15:30 — Talos buying power research (for OTC Options)

Eric asked how Talos does buying power calculations and how to utilize it for OTC options.

### What Talos provides: `CustomerCredit` WebSocket stream

Talos pushes a `CustomerCredit` message per account via a WebSocket subscription to the `CustomerCredit` stream. Each `DataItem` has:
- `Counterparty` — the account ID (clst_account)
- `Exposure` — current exposure (in use)
- `ExposureLimit` — max allowed
- `ExposureCurrency` — e.g., USD
- `ExposureDefinition` — optional descriptor
- `MarketAccount` / `Status` / `Timestamp` — optional metadata

Schema source: `libs/venues/crates/venues-talos-ext/src/schemas/talos.rs:551`

### How Pulse already uses it (for spot/HT)

**Integration already exists and is live for HT spot.** The flow:

1. `trade-engine/src/client_ws.rs` — `create_risk_checks_client_chain()` opens a WebSocket to `wss://{talos_config.ws_host}{talos_config.ws_path}`, authenticates with HMAC-SHA256 headers, and subscribes to the `CustomerCredit` stream.
2. `trade-engine/src/risk_checks.rs` — `TalosRiskChecksEventParser` parses incoming `CustomerCredit` messages and upserts into `RiskChecksCache` (keyed by account + currency).
3. `libs/prime/crates/cache/src/risk_checks.rs` — `RiskChecksCache` is a simple `HashMap<account, HashMap<currency, CustomerCredit>>`.
4. `trade-engine/src/execution_manager/handler.rs:177-206` — Before routing an order, handler looks up the account's `CustomerCredit`, computes `available_credit = exposure_limit − exposure`, and rejects if `order_notional > available_credit`.

**The check**: `available_credit = exposure_limit - exposure; if available_credit > 0 && order_notional > available_credit → reject`

### What "buying power" means in Talos

Talos doesn't call it "buying power" — it calls it credit/exposure. Talos tracks:
- **ExposureLimit**: max the customer can trade (set by CS risk team in Talos)
- **Exposure**: how much is currently "used up" (Talos calculates this from open orders + fills)

For OTC options, the question is whether Talos will calculate options premium exposure the same way as spot notional. That's the unknown.

### What needs to happen for OTC Options

The existing mechanism works for spot (notional USD check). For options:
1. **Talos needs to understand options premium exposure** — when a client buys an option, their "exposure" in Talos should be the premium cost, not the notional underlying. Unclear if Talos handles this automatically for OTC custom instruments, or if CS needs to configure it.
2. **Options instruments must exist in Talos** before Talos can track exposure against them (that's the custom_instrument flow Talgat + Chris are building).
3. **ExposureLimit must be set per account** in Talos by the CS risk team before any trade can pass the check.
4. **Haruko as long-term source of truth**: The Apr 22 plan was Haruko eventually becomes the consolidated buying power source. Talos is the MVP gate; Haruko is the longer-term risk view.

Key question for tomorrow's workshop: Does Talos calculate options premium exposure natively when the custom instrument is set up, or does CS need to push something to Talos to tell it what "exposure" means for an option position?

**Key answer to Eric's Talos question: Talos is NOT the buying power solution for options.**

Direct quote from this call: "Current challenge: Talos can only do account-level buying power, not coin-by-coin."

For OTC options, buying power/limit management goes through **Haruko**, not Talos. The architecture:

**Buying power: three client scenarios**
1. DVP-only clients: Credit sets limits based on financial due diligence; system pings Haruko for utilization
2. Custody-only clients: Out of scope for now
3. Bilateral swap clients: Consuming CS Derivatives desk-level limits, not individual client limits

DVP and custody buying power must not be mixed even for same entity. Risk-based buying power preferred (VAR or similar) over notional limits — accounts for different volatility profiles per coin.

**Margin call process (Haruko-centric)**:
- Haruko computes IA (Initial Amount) and IM (Initial Margin)
- EOD: Risk Portal pulls margin numbers from Haruko → creates margin calls → manages lifecycle
- When client wires collateral → automatically closes margin call → closure fed back to Haruko
- Intraday: prefer publishing valuations + margin numbers from Haruko → alerts in Studio

**Two integration options for Haruko↔Risk Portal**:
- Option 1 (preferred): Haruko publishes raw valuation + margin data to Risk Portal; alerts created/managed in Studio. More upfront work but strategic.
- Option 2 (fallback): Alerts defined in Haruko, triggered alerts consumed via email/Slack. Less work but throwaway risk.
