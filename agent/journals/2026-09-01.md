## 09:57
Eric hit `worker 'feeds-mktdata-DBT-bbo' error: ReconnectingWsClient( wss://test.deribit.com/ws/api/v2 ) Connecting`
after enabling a 700-instrument Deribit options chain on testnet.

Root cause in `ThrottledSubscriptionSender` (added in #3799, libs/venues/crates/venues-internal/src/mktdata/ws/subscription.rs):
`drain()` popped a queued subscribe request, spent a throttler token, then handed it to `WsSessionSender`,
which returns `Err` while the client is still handshaking (`build_ws_mktdata_feed_handler_with_client`
calls `connect_nonblocking()`, so enablement races the handshake). The error propagated out of the receive
chain to the worker AND the popped request was lost.

Fix: the throttled sender now holds the ws session lock directly and matches on `WsSendError`, so it can
tell "transport not up" from a real failure. A request leaves the queue and spends budget only once the
transport takes it; Connecting/Disconnected/Throttled clears the queue and returns Ok (the reconnect replay
of ActiveSubscriptions supersedes it); QueueFull holds the request; only Unrecoverable errors.
Added `test_handshake_in_progress_is_not_an_error`. venues-internal + venues-deribit tests pass, fmt clean.

Side note: Deribit splits at 250 channels/request, so 700 instruments is only 3 requests — pacing was never
the problem here, just the pre-connect send.

## Digital → Voyager rate integration: design investigation
Eric's framing: digital will compute a custom basket rate netted against OBFR, publish to a Kafka
topic in fleet (they already publish rates that way). Question: can voyager scrape the topic
directly, or does something need to store the rates first?

**Answer: store first. Don't have voyager consume the topic.**

Findings:
- **`apollo/services/rates` already exists and is the firm's rates service.** Go, stateful,
  HTTP :30000 + gRPC :20000. Postgres `rates.benchmark_rates(id, created_at, updated_at, date,
  type, rate)` and `rates.short_stock_rates`. `internal/driver/driver.go` *subscribes to Kafka*
  for file-upload notifications, loads, persists — and "skips processing on weekends".
  `internal/loader/benchmarks.go` pulls benchmarks from the NY Fed website (XML). Wired to
  Confluent schemaregistry in every env config. Serves consumers via generated proto client +
  `client_cache` (`ratespb.GetShortStockRate`, `GetFeeSchedule`).
- **But it's Go-only.** `fleetcli.config.yaml` gen targets are go / go-grpc / grpc-gateway — no
  Java. And voyager has ZERO references to it (`ratespb`, `apollo.rates`, `rates.*:20000` all
  absent). The two are completely disconnected today. Mitigating: grpc-gateway with
  `generate_unbound_methods=true` means there's an HTTP/JSON surface, so a Java consumer could
  hit REST without generating Java stubs.
- **Voyager's Kafka listeners (44 files) are all internal event handling, not external data
  ingestion** — snowflake-export, processing-records, cluster-commands, bk-sourcing,
  order-management. Notably order-management has `// TODO(SWAPS-1613): Kafka removed - listener
  disabled` — they've been *removing* listeners. Every external market data feed arrives via a
  `load-*-job` Spring Batch job: benchmark-rates, corporate-actions, eod-prices, fact-fx-rate,
  holidays, securities. Six of them, all Snowflake/FACT/Bloomberg sourced.
- **`voyager-market-data-loading-service` is NOT a general loader** — catalog.yml says "On demand
  security loading service for Voyager"; it's a REST security/OpenFIGI resolution service. Wrong
  home for rate ingestion. I'd earlier assumed it was the natural home; it isn't.
- Voyager's rate consumption is point-in-time historical, not streaming: `searchRates(codes,
  startDate, endDate)` with carry-forward baseline, `getMinUnfixedRateDate` + 10-day look-back,
  EOD reprocessing re-reads past dates. A topic cannot answer "what was the rate for date D as
  known today" — needs a materialized dated/versioned store, which is why their table carries
  `rate_date`, `source_load_time`, `version`, `deleted`.

Recommendation: keep the Kafka publish, land it in a dated rate store fleet-side, and have voyager
add a seventh `load-*-job` cloned from `load-benchmark-rates-job` with
`source_config_system = 'DIGITAL'` definitions. Lowest friction *for voyager* precisely because
it's a pattern they already run six times. The genericism should live in the rate record shape —
`(code, rate_date, rate, source_system, source_load_time, version)` — not in the transport.

Open design choice flagged to Eric: publish the all-in netted rate as its own benchmark code, vs.
publish the spread and let voyager apply it against an OBFR benchmark it already has (their model
has `RateConfiguration.spread` + `buildAllInRate = benchmarkRate ± spread`, so the spread form is
native — but the netting then gets reconstructed on their side and can drift).

## Scope correction from Eric + the landing-zone answer
Eric narrowed the question: OBFR/FACT is a non-issue, ALL calculation and netting happens in the
Pulse codebase, and Pulse publishes finished ready-to-consume rates to Kafka. The only open
question is what happens AFTER the topic. Dropping all the aggregation/netting design discussion.

**Key precedent found — digital already runs this exact shape**: `src/digital/.../haruko-push-prices`
(also `haruko-push-transactions`). Go service, `TEAM = "digital"`, 500m CPU / 1000 MEM. Consumes
Kafka topic `clearstreet.mktdata.markprice` via franz-go (`kgo`, consumer group,
`ConsumeResetOffset`), transforms `MarkPriceMessage` (JSON: sent/symbol/instrument_id/entries[])
into `AssetPriceRequest`, POSTs to Haruko REST at `/cefi/api/pricing/company/assets` with
venue `OTC`, priceType `COMPANY_MARK`. So: digital-owned Kafka→downstream-system bridge in fleet
is an established, deployed pattern owned by Eric's own org.
Also note: Pulse topics appear in fleet Kafka under a `clearstreet.` prefix, and that topic carries
JSON (not protobuf).

**Voyager's Snowflake contract is tiny.** `load-benchmark-rates-job` reads exactly three columns:
```sql
select RATE_DATE as rate_date, RATE_NAME as rate_name, RATE_VALUE as rate_value
from RATES.VW_BENCHMARK_RATES
where RATE_DATE > :last_loaded_date and RATE_DATE <= :business_date and RATE_NAME = :benchmark_code
```
plus a latest-date watermark query. Job config is just
`voyager.market-data.benchmark-rates.bulk-load: {start-date: 2024-03-26, source-system: FACT,
batch-size: 5000}`.

**Recommendation: land in Snowflake, let Voyager clone its existing job.** Digital owns a
haruko-style bridge (Kafka→Snowflake sink instead of Kafka→Haruko REST); Voyager's entire ask
becomes a cloned `load-*-job` with a new view name + `source-system: DIGITAL` + benchmark
definition rows. Voyager never touches the digital topic. This is both the lowest friction for
Voyager (same pattern they run 6x, same runbook/failure modes/watermark semantics as FACT) and the
most generic (a Snowflake view serves analytics/reporting/other services, not just Voyager).
Fallback if the Snowflake write path is blocked: bridge → a new Voyager write API (their benchmark
API is currently read-only, `POST /api/benchmark-rates/search` only), which costs Voyager more.

Also relevant: voyager's own `swaps-snowflake-export-service` (tier 2, prod) is already a
Kafka-consumer→Snowflake-JDBC-writer with `VoyagerBronzeDataSourceConfig` — so a bronze-layer
medallion structure exists and the in-house pattern is proven.

**Gap to flag in either option**: the job watermarks on `RATE_DATE > :last_loaded_date`, so a
*correction* to an already-loaded date is never picked up. Restatements need a manual reload or a
different watermark strategy. Same limitation exists with FACT today.

## Design doc written + open questions iterated
Wrote `tmp/digital-rates-to-voyager-design.md` (379 lines) per Eric's request. Then closed three
of the nine open questions against the code.

**Q2 RESOLVED — `accrueInterestForWeekends` is scopable.** `InterestProcessingContext
.getEffectiveProductConfig` resolves basket-level `ProductConfig` first, falling back to the
time-versioned pricing sheet. No global switch, so crypto baskets/sheets can differ from equity.

**Q3 RESOLVED — and it corrects my earlier analysis.** `TradeLotPositionCalculatingServiceImpl
.processTradeLotPositions` iterates `currentDate.plusDays(1)` with NO weekend/holiday skip, so
Sat/Sun `TradeLotPosition` rows are always generated. And there is zero weekend gating anywhere in
the interest handlers or position calc (grepped isDefaultWeekend/isNonBusinessDate/isNonWorkingDay/
SATURDAY/SUNDAY across both trees — nothing).
=> **Voyager already accrues 7 days/week.** I had told Eric that flipping
`accrueInterestForWeekends` was what would make Sat/Sun "get their own position rows" — wrong, they
already do. The flag only picks which day's *config* a weekend position resolves against:
true → `getLastDefaultWorkDay` (prior Friday), false/default → `getNextDefaultWorkDay` (next
Monday). Three days accrue across a weekend either way. So the digital-side requirement is just
"publish a row per calendar date + 7-day benchmark calendar"; the flag is an optional refinement.

**Q4 RESOLVED w/ caveat.** `MarketHolidayContainer.nonWorkingDays` is a data-driven
`Set<DayOfWeek>` so the 7-day calendar works. But `DateUtils.isDefaultWeekend` is hardcoded
Sat/Sun and calendar-independent; `getLastDefaultWorkDay`/`getNextDefaultWorkDay` build on it and
can't be configured away. They only govern `transactionDate` (config lookup), not
`rateObservationDate` (benchmark's own calendar), so the design holds.

**NEW FINDING (Q10) — likely boolean mix-up in voyager.** `ResetConfiguration.getForPositionType`
has exactly one overload; 4th param is `resetImmediatelyAfterObservation`.
`FinancingCalculationDetailsResolverImpl` passes `interestResetAfterObservation` (correct), but
`InterestUtils.getBenchmarkRateContainer` passes `accrueWeekends` into the same slot, and both
interest handlers feed it `accrueInterestForWeekends`. Defaults differ (false vs true), so for
SETTLE_DATE positions the two paths disagree today. Blast radius looks limited to
`resetRateObservationDate`, one of three inputs to a `DateUtils.min(...)` setting the benchmark
fetch window start — probably masked by the other two terms, which is likely why it's gone
unnoticed. Directly relevant to us: enabling `accrueInterestForWeekends` for crypto would also
silently flip settle-date reset observation for those baskets. Flagged as suspicion, not confirmed
defect — needs `deriv` review.

Remaining open: Q1 (RATE_NAME scheme), Q5 (revisions), Q6 (gap policy), Q7 (backfill history),
Q8 (Snowflake schema + write path), Q9 (is daily grain enough — product), Q10 (the mix-up).

## Schedule decision: keep 0 17 * * * ET
Eric decided not to change the cron — the digital job will match the FACT job's
`0 17 * * *` America/New_York, and Pulse absorbs the constraint via publishing requirements.
Removed it from open decisions; §11.6 now records the decision and the derived requirements.

Math: 17:00 ET = 21:00 UTC (EDT) / 22:00 UTC (EST), so the job never starts before 21:00 UTC and
the UTC date at job time always equals the ET date — no rollover off-by-one. For 8-hourly perp
funding (00:00/08:00/16:00 UTC), the last interval of UTC date D closes at 16:00 UTC, ~5h before
the job runs on that same date. Comfortable fit.

Derived requirements written into the doc:
- **P2-1**: complete fix for RATE_DATE = D visible in the view before **21:00 UTC on date D**.
  Target 21:00 year-round rather than tracking DST (EST window is an hour more generous).
- **P2-2**: a date's rows must appear **atomically** — the job can read mid-write and would treat
  a partial day as complete. Write all names, then expose in one commit (flip IS_CURRENT, or
  stage-and-swap).

Miss behavior: data self-heals (watermark `RATE_DATE > :last_loaded_date` means the next run picks
up D and D+1 together), but accrual may not — date D's EOD will already have run without a rate,
throwing `Unable to find benchmark {code} for {date}` and failing to post interest. Whether the
next cycle reprocesses D is unconfirmed → new Q12 for deriv. So 21:00 UTC is a hard SLA needing
alerting, not a target.

Also confirmed the FACT cron is `* * *` not `1-5`, so weekend/holiday runs already happen — which
is exactly what 7-day crypto rates need. No change required.

## CORRECTION: 7-day calendar is NOT config — it's hardcoded
I asserted three times (twice in the doc, once to Eric) that a 7-day calendar was expressible in
data because `MarketHolidayContainer.nonWorkingDays` is a `Set<DayOfWeek>`. Wrong. The field is
data-shaped but there is exactly ONE construction site in the codebase and it hardcodes:

```java
// MarketHolidayInfoServiceImpl.buildHolidayInfo:54
new MarketHolidayInfo(descriptor, dateRange, holidays, Set.of(DayOfWeek.SATURDAY, DayOfWeek.SUNDAY))
```

Verified: `grep 'new MarketHolidayInfo('` outside tests returns only that line; `setNonWorkingDays`
is only called in a test fixture.

Consequence: Sat/Sun are non-business dates for EVERY benchmark calendar, so `rateObservationDate`
for a weekend position rolls back to Friday and any Sat/Sun rate we publish is silently never read.
Crypto positions would accrue the weekend at Friday's rate. That's the SOFR convention and is
defensible — but it must be a decision, not an accident. Now D1 in §11.7 with two options:
D1a accept Friday carry-forward (no code change, weekend rows pointless) vs D1b change
`MarketHolidayInfoServiceImpl` to vary non-working days per calendar (shared code, serves every
benchmark calendar incl. equity swaps, bigger review; must default to Sat/Sun for existing rows).

Lesson for this subsystem: a `Set<DayOfWeek>` field being data-shaped says nothing about whether
any data path populates it. Check construction sites, not just the model.

Also learned while verifying:
- `MarketHolidayType` enum = BANK / TRADE / SETTLEMENT; `MarketHolidayCodeType` = CALENDAR /
  COUNTRY / CURRENCY / MIC. But `marketHolidayCode` is a free String, so a new calendar code can be
  minted without an enum change.
- Holiday rows load from `swapsmonitor_ref.clearho` (Swaps Monitor vendor feed) via
  `load-holidays-job`, keyed by calendar code, filtered to types 'SE TRADING'/'SE SETTLEMENT'/'BANK'.
  A minted crypto code has no rows there — whether `ensureDateIsLoaded` tolerates a calendar with a
  valid range but zero holidays is UNVERIFIED and flagged in D3.

## D1 DECIDED: D1b — weekend logic in Voyager
Eric chose weekend logic in Voyager if supported. It is. Verified the change is small:

`MarketHolidayInfoServiceImpl.buildHolidayInfo` is a single private method that ALL four public
resolvers (ByCalendar/ByCountry/ByCurrency/ByMic) and all six controller endpoints funnel through.
The fix is replacing `Set.of(DayOfWeek.SATURDAY, DayOfWeek.SUNDAY)` with a lookup on the calendar
code — already in scope as `holidayEntry.getKey()` — defaulting to Sat/Sun. Default-preserving, so
equity swaps are bit-identical; that's the review argument. No schema change (config property).

**Closed the D3 unknown**: `MarketHolidayServiceImpl.getHolidaysFromCache` builds its result map
from the REQUESTED codes, `holidays.getOrDefault(code, DateIntervalMap.empty())`. So a calendar
code with zero holiday rows still materializes with an empty set — a minted crypto code needs
nothing in the `swapsmonitor_ref.clearho` vendor feed, and `dateRange` comes from the request so
`ensureDateIsLoaded` is satisfied.

**Isolation property for the review**: benchmark calendar and trade basket calendar are separate
lookups — rate observation uses `holidayCalendars.get(benchmarkDefinition.getHolidayCalendar())`,
reset scheduling uses `context.getTradeBasketBusinessDateCalendar()`. Making a benchmark calendar
7-day does NOT change reset scheduling. Follow-up (not Phase 1): whether crypto trade baskets
should also be 7-day, which would affect resets and `advanceDate`.
