
## Investigation: instrument_id 18925090 / CLST.SPOT.OPENAI-USD missing in cs-dev

Eric reported instrument_id 18925090 not assigned to CLST.SPOT.OPENAI-USD in cs-dev.

Traced the assignment chain (pulse repo):
1. FACT source topic `clearstreet-msk.dauntless.instrument.instruments_events`
2. `clearstreet-instruments-puller` (app/crates/clearstreet-instruments-puller/src/service.rs)
   - filters via `classify_clst_instrument` (libs/prime/crates/refdata/src/clst.rs:44)
   - keeps type=="cryptocurrency" (spot), or type=="crypto" AND exchange=="XXXX" (options)
   - re-keys by instrument_id, publishes to `fact.instruments.cache` (compacted)
   - is_active==false => null payload (tombstone)
3. `ClstInstrumentsCacheUpdater` consumes cache topic, keys by normalized Symbol
4. `ClstRefDataAugmentationService` (clst.rs:353+) stamps
   `InstrumentDefinition.clst_instrument_id` into refdata

Findings in cs-dev (clearstreet-dev-prime-tokyo):
- `fact.instruments.cache`: 2562 distinct keys, full read. ZERO hits for OPENAI or 18925090.
- `CLST.SPOT.ANTHROPIC-USD` IS present (type "Cryptocurrency", exchange XXXX,
  description "Anthropic PBC Private Equity") -- so the tokenized-private-equity
  shape parses and classifies fine. Not a symbology problem.
- Puller consumer group lag == 0, fully caught up to offset 99742042.
  So the puller HAS seen every source record; it did not simply miss it.
- Symbol::try_from("CLST.SPOT.OPENAI-USD") parses cleanly (no asset whitelist).

Remaining causes to distinguish: (a) never published to FACT cs-dev,
(b) published with is_active=false -> tombstoned + compacted away,
(c) published with a type other than cryptocurrency/crypto -> UnsupportedType drop.

Side finding worth raising separately: 12 CLST.SPOT symbols in cs-dev carry
MULTIPLE distinct instrument_ids (ANTHROPIC, AVAX, BABA, BTC, COIN, ETH, HYPE,
INTC, LINK, LIT, SOL, XRP). refdata lib.rs:1523-1541 handles the collision by
keeping the first claim in the reverse map and warning; the forward
clst_instrument_id is last-writer-wins. Duplicate FACT ids per symbol in dev
means id->symbol lookups are ambiguous.

### ROOT CAUSE FOUND

Raw FACT record (source topic segment 00000000000097641567.log, CREATE
2026-09-04T20:33:13.979563Z, UPDATE 20:37:56.326522Z):

    "instrument_id":"18925090"
    "name":"CLST.SPOT.OPENAI-USD"
    "description":"OpenAI Private Equity"
    "exchange":"XXXX"          <- internal, correct
    "sector":"Crypto"          <- correct
    "is_active":true           <- correct
    "crypto_instrument":{"underlying_digital_asset_id":"68"}   <- correct
    "type":"Common Equity"     <- ***THE PROBLEM***

`classify_clst_instrument` (libs/prime/crates/refdata/src/clst.rs:44) only keeps:
  - type == "cryptocurrency"                    (spot)
  - type == "crypto" AND exchange == "XXXX"     (internal options)
Everything else -> ClstInstrumentClass::UnsupportedType -> dropped by the puller
at clearstreet-instruments-puller/src/service.rs:56-62.

"Common Equity" matches neither, so the record is dropped, never reaches
`fact.instruments.cache`, never enters ClstInstrumentsCache, and
ClstRefDataAugmentationService never stamps clst_instrument_id onto the symbol.

Contrast CLST.SPOT.ANTHROPIC-USD -- same product shape ("Anthropic PBC Private
Equity", exchange XXXX, sector Crypto) but FACT tagged it type "Cryptocurrency",
so it passes. This is an upstream FACT taxonomy inconsistency between two
tokenized-private-equity listings.

Observability gap: the drop is `log::debug!` and the puller runs at INFO
(0 DEBUG lines in the pod log), so nothing surfaces. There is a stat for
invalid-symbol skips (clst_instruments.skipped_invalid_symbol.count) but none
for UnsupportedType drops.

Fix options:
  1. Upstream: have FACT correct type to "Cryptocurrency". Puller is caught up
     (lag 0), so a new UPDATE event flows through automatically.
  2. Pulse-side: make classify_clst_instrument key off the stronger signals
     (exchange=="XXXX" + crypto_instrument populated) rather than the brittle
     `type` string allowlist.
  3. Add a stat + warn for UnsupportedType drops so this is not silent.

NOT verified: whether prod (clearstreet-prime-tokyo) has the same gap -- the
prod kafka read was blocked by the permission classifier.

### Kafka record headers on the refdata topic (cs-dev) — reusable

Chasing a manual republish of INSTRUMENT.CLST.SPOT.OPENAI-USD, learned the
header contract (libs/transport/crates/kafka/src/rdkafka/producer.rs:398-425):

  cidx  u32 LE  chunk index      } added automatically by the producer's
  ccnt  u32 LE  chunk count      } chunking layer
  sts   i64 LE  send time (Utc::now().timestamp_millis()) — producer stamps
                its own, then copies through any other headers. That is why
                system records show TWO sts headers: upstream's + this one.
  enc   6 bytes EncodingInfo = format u16 LE, schema_id u16 LE, message_id u16 LE

  enc for refdata records: 02 00 0A 00 03 00 = format 2, schema 10, INSTRUMENT (msg 3)
                           02 00 0A 00 02 00 = same but ASSET (msg 2)

The 0x0A in enc is just the low byte of schema_id 10 -- but it is a literal
newline, and together with the NUL bytes that makes `enc` impossible to express
in kafka-ui or kafka-console-producer, which only take string header values.
That is why two hand-publishes in a row landed without it (offset 1024413 had
NO_HEADERS at all; 1035854 had cidx/ccnt/sts but no enc).

RESOLUTION: don't hand-craft the headers. Eric added a min-price field via the
admin endpoint and let the app's own producer republish the record -- the
producer stamps enc/cidx/ccnt/sts correctly by construction. Publishing through
the app is the right move any time a record needs the binary enc header.

If a raw inject is ever genuinely needed, tools/crates/kafka-inject takes
base64 key/value/headers (its counterpart is kafka-capture) -- though its
headers field is a BTreeMap, so it cannot represent the duplicate sts.
