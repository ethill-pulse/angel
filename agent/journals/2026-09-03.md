## SIGN AUDIT COMPLETE — one rate is SAFE; found a real pre-existing bug (now §16 of design doc)
**Answer to Eric's question: YES, Voyager handles the position side correctly.**
`LotType.direction()` (LotType.java:46-58) is a true ±1 multiply — LONG→v, SHORT→v.negate() —
sign-PRESERVING, not a force-the-sign. Valuation is always non-negative (openQuantity stored absolute),
so the side isn't baked in. charge = direction(dailyAmount.negate()). Four-cell matrix fully
antisymmetric; negative rates need no special handling. HALF_UP is an odd function so round(−x)=−round(x).
LedgerEntryType carries NO sign and all transaction-ledger consumers are purely additive → no double
negation. **Back-to-back invariant holds: at spread=0 the pair sums to ALGEBRAICALLY zero**, and at
spread≠0 the residual is the intended −2Vs/D which does NOT flip when funding goes negative.
Existing `16_Spread_Exceeds_Benchmark.feature` is effectively the mirror test — SHORT at +4.83% and
LONG at −4.83% assert identical amounts. Passes.

**BUG FOUND (pre-existing, ours to surface): `TradeBasketAccrualProjectionServiceImpl.java:282-285`**
uses `MoneyAmount.sign(oppositeSide.getLotSign())` = `|value| × sign` (NumberUtils:102-112), which
DISCARDS the input sign, where the handlers use `direction(dailyAmount.negate())` which PRESERVES it.
Agree only when dailyAmount ≥ 0. For negative all-in rates the PROJECTION is sign-inverted vs what the
ledger actually posts, and at spread≠0 the projected pair residual inverts too — showing the firm
paying a spread it earns. Ledger money is unaffected; this is the projection API + basket-info screen.
Latent today (negative all-in is already a tested ledger state) but perp funding makes it the COMMON
case. Sits in a completely untested quadrant — projection suite has no SHORT and no negative rate.
One-line fix. → for Yoon.

**The one asymmetry surviving spread=0: `selectFixingConfig` (FinancingCalculationDetailsResolverImpl
:234-241).** SHORT may use getShortBenchmarkFixingConfig() while LONG always uses the default →
different lookBackDays → different rateObservationDate → different rate on the same business date.
Residual ∝ day-over-day funding change. Mitigation: pin Short Benchmark Look Back == Benchmark Look
Back on perp baskets, or use basket/trade-level overrides which are lot-type-AGNOSTIC and structurally
safer for back-to-back.

**Config divergence vectors (not bugs, operationally load-bearing):** long vs short RateConfiguration
have independent benchmark code AND spread (:366-368); SHORT with stock-loan posting gets its financing
spread forced to zero and an extra STOCK_LOAN_FEE entry (:405); shouldPostInterest gated per side
(FinancingCalculationDetails:44-54). For perp baskets: same benchmark both sides, stock-loan OFF, both
post flags ON.

**Test gap:** NOTHING in the suite asserts long/short antisymmetry — every pairing deliberately uses
different spreads, and all BUY/SELL pairs are separate Scenario Outline rows, never netted. Recommended
test: one basket, LONG+SHORT identical notional/benchmark/date, spread 0, assert sum == 0, at both +r

**Undetermined:** whether any NON-Voyager consumer of LONG_INTEREST/SHORT_INTEREST (reporting extracts,

## Pulse recon results + Phase 1 spec written (tmp/pulse-funding-rates-phase1-spec.md, 348 lines)
High-value findings from the Pulse recon agent, all now captured in the spec:

**The existing `mktdata.fundingrate` topic has three traps:**
1. It carries the GENERIC `MarketDataStatistics` (market_data.yml id 12), and **the funding rate rides
   in `entries[].price`, NOT `entries[].rate`** — that type has no `rate` field (commented at

2. It's **JSON, not protobuf** (`RecordEncoder::new(Format::Json)`, main.rs:193).
3. **Publishing is gated on `instrument_id.is_some()`** (markprice.rs:235) — a perp with no mapped CLST
   instrument ID never reaches the topic at all.
Also: no Kafka key, partition 0, dedup on settlement ts. `entries[].ts` IS the settlement timestamp.
**Nothing consumes the topic today — we'd be the first consumer.**

**NO venue normalization exists anywhere.** Every venue passes its raw decimal through. No sign, no
units, no scaling, no shared helper. The ONLY sign-aware code is the validator explicitly EXEMPTING
funding rate from its negativity check (validator.rs:431-432). And `settl_price_type` is assigned
inconsistently, which combined with the Final-only filter silently determines venue coverage:
  reaches the topic (Final): Binance REST, Bybit, BitMEX, Kraken, Bitstamp
  silently dropped (Theoretical): Binance WS, OKX, Bitget v2+UTA, MEXC
  Bitfinex: emits no FundingRate entry at all

**Funding interval length is NOT discoverable.** `MarkPrice.next_funding_time` exists and 6 venues set
it, but nobody reads it and it never reaches the topic. Refdata's `InstrumentDefinition` has NO funding
fields (no interval, cadence, contract type, or linear/inverse). BitMEX's `fundingInterval` is in its
venue schema but never mapped; Bybit's is in test JSON only and not even in its schema.
=> **Resolved by design: SUM the day's interval rates rather than mean × assumed count.** Summing needs
no interval-count assumption at all, and stays correct when cadence changes mid-day. This sidesteps the
whole gap — my earlier "don't hardcode 3/day" advice becomes moot.

**Only Binance has a pull API**: `get_funding_rate_history(symbol, start, end, limit) -> Vec<MarkPrice>`
(venues-common/src/apis/mktdata.rs:19-28, default impl errors; impl at venues-binance/.../dma.rs:184-198).
"Settled funding rates, oldest first, exact funding timestamp in ts." => **Recommended D1.1: pull, not
stream.** Stateless, backfillable, restart-safe, removes the "were we up at 16:00 UTC" failure mode.

**Patterns to build on:** `spot-trade-recon` is the structural match (a whole app doing only a periodic
lookback computation, `config.lookback_secs` + `run_periodically`, missed window covered by next tick).
`clearstreet-stats-publisher` is the windowing analogue (daily session window, tz-aware `next_close()`
at service.rs:79-118 handling ambiguous local times). `calc_timestamp_at_boundary(ts, duration)` from
kafka-candle-calculator is reusable for a 24h window. `Runtime::run_periodically` is first-class
(runtime/src/lib.rs:724-742, Schedule = Cron|Interval, ~40 call sites).

**Recommended shape: periodic task in a long-running app, NOT a CronJob** — the app needs RefDataCache
and RefDataManager's mandatory 3-step init (new → await_recovery → run_continuously); a CronJob would
pay full refdata recovery every run.

**Two config traps:** (a) Pulse's 3-step pipeline — **skipping the conductor provider compiles fine and

**Recommended new message schema rather than reusing MarketDataStatistics** — that type can't carry day
count, interval count, or the window, so the rate wouldn't be self-reconstructing.
**Units: publish DECIMAL on Kafka**; the percent conversion Voyager needs belongs in the Snowflake

## D2.3 DECIDED by Eric + 4pm ET cut-off analysis
Eric's architecture: single thread, sensible order building a cache, individual rates first then
netting, **cannot net nets** (legs are always individual rates), fixed 16:00 ET.

**What it resolves:** D2.3 → option A (compose from Phase 1 daily rates, not raw intervals), so Phase 2
is a thin layer not a restructuring. And "cannot net nets" is the valuable part — it bounds the
dependency graph to exactly TWO levels, which removes cycle detection, topological sort/dependency
resolution, memoisation depth, and partial-visibility handling. Cache becomes a flat symbol→rate map,
written once in stage 1, read-only in stage 2. Validation reduces to "every leg resolves to an existing
leaf", checkable before any computation. Single-threaded is right regardless — bounded symbol set, once
a day, determinism >> throughput.
Accepted limitation: no basket-of-baskets. Deliberate, fine for Phase 2, and cheap to relax later
(allow stage 2 to read stage-2 output, which then needs the dependency resolution) — an addition, not
a rework, which is what makes the constraint worth holding.

**What it does NOT resolve — said plainly:** D2.1 (which notionals, as of when), D2.2 (target weights vs
actual positions), D2.4 (mid-day rebalances) are untouched. His proposal is execution architecture, not
weighting economics. Those remain the substance of Phase 2.

**4pm ET turns out to be well-chosen for a structural reason.** 16:00 ET = 20:00 UTC (EDT) / 21:00 UTC
(EST). 8h funding settles 00/08/16 UTC, so BOTH cut-offs land in the dead zone between the day's last
settlement (16:00 UTC) and the next day's first (00:00 UTC). A trailing 24h window from there captures
exactly the 3 settlements of the UTC calendar day under both EDT and EST, and the rate's business date
is unambiguously the UTC date (= the ET date at that instant).

**NEW ISSUE I found: a fixed local cut-off + fixed 24h lookback breaks at DST.**
  spring forward → consecutive 16:00 ET runs are 23h apart → windows overlap 1h → DOUBLE COUNT
  fall back     → 25h apart → 1h gap between windows → MISSED settlements
8h cadence is safe by luck (the affected hour is inside the dead zone). **4h cadence is not** — a 20:00
UTC settlement sits exactly on the boundary. 1h cadence breaks outright.
Fix (cheap, strictly better): define the window as `[previous cut-off, this cut-off)` rather than
`[now − 24h, now)`. Windows then abut exactly by construction regardless of DST or a missed run.
Demoted `lookback_hours` to `max_catchup_hours` (bound for catch-up only). Reuse
`clearstreet-stats-publisher`'s tz-aware `next_close()` (service.rs:79-118) rather than reimplementing.
Added a test-plan entry requiring the DST test use a **4-hourly** symbol — an 8-hourly one passes either
way and proves nothing.

**Operational risk: exactly 1 hour of margin.** Voyager's job is 17:00 ET and both are ET-anchored, so
the margin is 1h year-round. That hour must cover compute → Kafka publish → bridge consume → Snowflake
write visible. Thin for a daily financial job — argues for alerting on "not published by 16:15 ET"
rather than finding out when the consumer reads nothing.

## Perp funding is SNAPSHOT-based, not time-weighted — and it creates a real basis
Eric asked whether Binance considers position length (e.g. held 4h → pay half?). **No.** Funding is
`position notional at the funding instant × funding rate`, using the mark price at that instant. Held
7h59m and closed a minute before the timestamp → pay NOTHING. Opened a second before → pay the FULL
interval. Entirely binary, no pro-rating. (Hence funding-timestamp sniping as a known strategy.)

**Why this matters for the swap wrapper — an implicit assumption breaks.**
Voyager accrues `position notional × allInRate ÷ dayCount` once per business date off a DAILY position
snapshot. Actual funding is THREE discrete snapshots at specific instants. They agree only when the
position is constant across the day.
  constant all day               → 3 intervals actual vs 1 day accrued → equivalent ✓
  opened 17:00 UTC, held through → 0 actual on day 1, but a full day accrued
  opened AND closed inside one 8h window → ZERO actual, but a full day accrued
So an intraday client can be charged funding they never caused, or cause funding they aren't charged.

**Where the exposure lands:** the back-to-back chain uses the same daily-accrual model at every INTERNAL
hop, so those legs offset. The mismatch is at the OUTERMOST hop — CS's hedge pays the venue SNAPSHOT
funding while the client is charged DAILY-ACCRUED funding. That delta is basis risk CS eats or earns.
Materiality depends entirely on client behaviour: negligible if clients hold for days, material and
systematically biased toward whoever understands the timestamps if they trade intraday.

**Does NOT change Phase 1** — the published rate is correct either way; the mismatch is in how the rate
is APPLIED downstream (Voyager's accrual model), not in the feed. But it needs to be understood before
these rates drive client-facing interest, and if the answer is ever "we need position-time-weighted
funding," that's an accrual-engine change, not a rate change.

## Missed-run durability — D1.9 resolved toward CronJob, hourly idempotent catch-up
Eric asked how we guarantee the cronjob fires if the process was down: restart check, or a more durable
scheduler than `run_periodically` + cron?

**Platform answers most of it.** Pulse's `[deploy.cron]` ships reboot-resilient defaults: `Forbid`,
`starting_deadline_seconds = 3600`, `OnFailure`, `backoff_limit = 6`. INFRASTRUCTURE.md states outright
that "a run missed during downtime still fires when the cluster is back."
=> **Decisive argument for the CronJob shape**: the scheduler lives in the K8s CONTROL PLANE, not in the
process. `run_periodically` inside a Deployment means the schedule dies with the pod — down at the
cut-off = nothing fires and nothing records that anything was missed.

**But scheduling durability alone isn't enough.** startingDeadlineSeconds=3600 covers only 1h of
downtime; beyond that K8s marks the run missed and SKIPS it. And that same hour is exactly the margin to
the 17:00 ET Voyager job — a pod starting 59 min late publishes with zero slack.

**Real answer: lean on idempotency, not on scheduling.** Draining the topic and recomputing gives the
same answer, and the topic holds 7 days, so a missed run is a DELAYED PUBLISH, not data loss. Reframe
the job from "compute today" to "compute what's missing":
  each run: for each business date whose window has CLOSED and is NOT yet published → drain, compute, publish
Then schedule it **hourly** (`0 * * * *`) instead of daily:
  - missed cut-off fire self-heals within the hour
  - downtime beyond the 1h starting deadline self-heals on the next fire
  - NO startup catch-up code needed — every run IS a catch-up run
  - and it DISSOLVES the DST/cluster-timezone cron wrinkle I raised earlier: cron becomes plain hourly
    and the 16:00 ET boundary is computed internally, tz-aware
Precedent: `spot-trade-recon` runs `0 */{} * * * *` with a lookback and comments that a missed window is
covered by the next tick.

**Where the "already published" record lives: read back the OUTPUT topic.** Drain it, collect existing
(symbol, business_date) pairs, skip them. Symmetrical with the input design, fully stateless, zero new
infrastructure. Requires output retention >= the catch-up window; the eventual DB becomes the natural
home later.

**Two operational requirements added:** (a) alert independently of self-healing — a window unpublished
at ~16:15 ET should page even though the next run would fix it, else the first signal is the consumer
reading nothing; (b) `Forbid` means a slow run blocks the next, so emit a run-duration metric — if it
ever nears an hour, hourly runs start SKIPPING rather than overlapping.
Test plan gained: missed-fire recovery with no startup-specific code path, and an idempotency test
(run twice → second publishes nothing).

## CORRECTION — Eric overrode the CronJob: long-running process with startup resume
He wants a running process, NOT kubernetes-driven. On startup, check where the egress topic left off and
continue from there; predictable publish ordering makes that easy.

**He's right and it's stronger than my recommendation.** A CronJob's
`starting_deadline_seconds = 3600` means downtime beyond ONE HOUR gets the run marked missed and
SKIPPED. A Deployment is restarted by K8s on crash and then resumes from the egress topic, so an outage
of ANY length recovers fully. No cliff. I'd anchored on "externalise the scheduler" and missed that the
startup-resume approach makes the scheduler's durability irrelevant.

**Sort order: `(business_date ASC, symbol ASC)`**, symbol lexicographic on the CLST string. Gives resume
WITHIN a partially-completed date, not just between dates — died after 6 of 20 symbols on date D →
continue at symbol 7.

**Two requirements I flagged that must hold for "resume after last" to be safe:**
1. **The topic must contain a CONTIGUOUS PREFIX.** With concurrent publishes, if #7 succeeds while #5
   fails, the tail is #7 and #5 is skipped PERMANENTLY AND SILENTLY — every future startup also resumes
   after #7, so the gap never heals. Fix: publish sequentially in sort order with `acks=all`, confirming
   each ack before the next. Few hundred records/day so throughput cost is irrelevant.
2. **The egress topic must be SINGLE-PARTITION.** Kafka orders only within a partition, so multi-
   partition has no global resume point. Pin it explicitly in topic config — a later partition increase
   would break resume silently rather than loudly. (Ingress topic already does this: partition 0, unkeyed.)

**Recommended refinement: drain the egress topic on startup, don't just tail it.** Position-based resume
does NOT backfill a newly configured symbol for dates already published (resume point is past them).
The egress topic is tiny (7 days × symbols × 1 record = hundreds), so a full drain costs the same and
additionally self-corrects on config change AND detects gaps for free — making requirement 1 belt-and-
braces rather than the sole guarantee. Keep the sort order regardless for auditability.

Deployment note updated: NO `[deploy.cron]`; auto-detection (`kafka` dep, no `webserver`) already gives
ingress=false / background-worker / namespace=kafka, so `infrastructure.toml` needs only an empty
`[deploy]`. Cut-off schedule lives in-process via `run_periodically` evaluated tz-aware against
America/New_York — no cluster-timezone dependency, DST cron wrinkle gone.

Test plan rewritten for this shape: clean startup resume; mid-date resume (N of M symbols); gap safety
(inject a hole, assert detected+filled not resumed past); idempotency (nothing missing → zero published);

Right, and worth naming: **backfill is the normal path, not a mode.** No `--backfill` flag to rot; the
cold-start path IS the steady-state path with an empty published set, so it's exercised on every process
start. Clean dev loop: wipe the egress partition, restart, deterministic full recompute.

**Two things I added to make cold start safe:**

1. **Respect the retention edge.** On cold start the oldest ingress records sit at the retention
   boundary, so the earliest business date may be missing settlements that already aged out. Summing
   what remains gives a WRONG rate (under-summed, silently plausible), not a missing one. The
   expected-count check alerts but the bad value would still publish. So:
       T_min = timestamp of the OLDEST RECORD ACTUALLY READ
       earliest publishable window = first cut-off boundary >= T_min; skip anything older
   Derive T_min from what was read, not a separate query — retention moves during the drain.
   This only bites on cold start / after a long outage: least exercised in prod, MOST exercised in dev.

2. **The downstream must be idempotent.** Because wipe-and-restart is an intended tool, republication is
   a NORMAL operation in this design. The Snowflake bridge must **upsert on (RATE_NAME, RATE_DATE)**,
   not append. The table shape already anticipates this (VERSION / IS_CURRENT in the Voyager design
   doc), but it's now a hard requirement on the bridge rather than implied. In prod, wiping the egress
   partition triggers a full republish the bridge re-ingests — safe if it upserts, duplicate rows if not.

Test plan gained: cold start = full backfill (empty egress + populated ingress → every fully retained
date computed in sort order), and the retention-edge case (earliest partially retained date is SKIPPED,
not published under-summed).

## THE BUG (verified myself, then Eric steered me to the right analogue)
`impl crate::Consumer for DynamicKafkaConsumer` (libs/transport/.../rdkafka/consumer.rs) implements
**only `poll`**. The trait defaults `last_consumed_at` and `last_transient_error_at` to `None`. So on a
DynamicKafkaConsumer — which our drain used — `erroring` is permanently false: the
`MAX_DRAIN_BROKER_OUTAGE` abort is unreachable and `CLOUD_BACKOFF.idle` never engages. Correctness is
fine (watermark-bounded drain), but the LIVENESS guard is absent — a mid-drain outage spins at the
100ms poll timeout until shutdown with nothing reaching the alert pipeline.

**I moved position twice; the final read is the right one.**
- First I proposed a wall-clock drain deadline instead. **Wrong** — Eric pointed at scalesets, then
  better, at the refdata cache populator. `RefDataManager::await_recovery`
  (libs/prime/crates/refdata/src/lib.rs:226) uses the IDENTICAL idiom, comments included. So the agent
  hadn't invented the guard, it had faithfully copied the house pattern; a bespoke deadline would have
  been a divergence.
- Then: is refdata broken in production too? **No.** `impl RefDataManager<KafkaConsumer,
  KafkaMetadataClient>` — `new()` builds a **KafkaConsumer**, which DOES override both methods. So the
  guard works across all 20+ apps that hydrate refdata.
- The structural difference: refdata assigns a FIXED topic-partition and forces
  `SeekBehavior::Beginning` once at construction (and errors if configured otherwise). Ours re-seeks
  every cycle, which is why it reached for Dynamic.
- **Root cause is the `None` trait defaults** — they turn "wrong consumer type for this pattern" into a
  silent no-op instead of a compile error. Anyone copying the refdata idiom onto a Dynamic consumer
  hits the same trap.

**Eric's call: fresh-consumer route. Agent implementing now.** Replace the re-seeking
DynamicKafkaConsumer with a fresh `KafkaConsumer` per drain, modelled on refdata's construction — a new
instance with a fixed topic-partition + SeekBehavior::Beginning re-reads from the start by
construction, so the re-seek dance goes away and the guard becomes live with NO shared-library change.

## JWT re-auth explained — and fcmin's version has two defects
Eric asked what the JWT re-auth is about. Read `apollo/services/fcmin/internal/snowflake/db.go`
directly rather than relaying the agent's summary.

**What it is:** Snowflake auth here is KEY-PAIR, not password — that's the `-pk` in
`svc-<service>-pk`. gosnowflake mints a **JWT signed with the private key** at authentication time,
with a bounded lifetime. On lapse, queries fail with `390114` (auth failure) / `390144` (jwt token
invalid). fcmin traps both on `*gosnowflake.SnowflakeError` and calls `openDB` again, which re-invokes
`getConnStr()` and opens a fresh `*sql.DB`. Wraps `Ping` and `Transact`.

**Why it hits us HARDER than fcmin:** our service is long-running and near-idle — one message per
symbol per day — so the Snowflake connection sits untouched ~24h between uses. And
`SetMaxIdleConns(2)` means the pool RETAINS idle connections rather than dropping them, so it hands
back a stale one. Failure shape: start → authenticate → idle a day → first MERGE → 390114. Exactly our
daily cadence.

**Subtle but important:** `getConnStr` is a `func() (string, error)`, not a string. So re-auth re-reads
the credential source and picks up a ROTATED Vault static-cred. Easy to lose when copying.

**TWO DEFECTS in fcmin's version I caught and told the agent NOT to inherit:**
  1. **Data race** — `t.db = db` in `reauthenticate()` is an unsynchronised write while `Transact` and
     `Ping` read `t.db`. Needs a mutex or atomic.Pointer.
  2. **Connection leak** — the old `*sql.DB` is never `Close()`d, so its pooled connections leak on
     every re-auth.
Neither likely bites a single-threaded consumer, but there's no reason to propagate them into a new
service. Also told the agent to make sure the wrapping covers the path that actually performs the
MERGE, not just the entry points fcmin happened to need.

Sent as a correction to the running implementation agent (it was mid-build and I'd explicitly told it
to "copy fcmin's handling").

**Rounding done well, and it surfaced two things I hadn't anticipated when briefing it:**
1. **Rounding can CARRY INTO THE INTEGER PART.** `9999999999.99999999999999999` has 10 integer digits
   but rounds to `10000000000` = 11, which doesn't fit NUMBER(26,16) — exactly the redeliver-forever
   case the integer check exists to prevent. So Validate's integer check now runs against
   `roundToScale(d)`, with the rule factored into one function so it isn't written twice. Verified in
   the source myself.
2. **`decimal.String()` trims trailing zeros** — `"5.4000"` parsed and re-rendered returns `"5.4"`. So
   `roundedForColumn` returns the record UNTOUCHED when scale already fits, rather than round-tripping
   every value. Had it rendered unconditionally the exact-string guarantee would have silently broken
   on the most common input.
It also confirmed the rounding mode empirically rather than trusting docs, using discriminating cases
where half-to-even would differ (`5.40000000000000005` → `5.4000000000000001`, 16th decimal even),
pinned in both signs.
