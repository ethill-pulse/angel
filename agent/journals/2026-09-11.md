
## Studio UI + FX trading — research
Eric asked whether Studio UI supports FX trading. Dug through Notion (Prime / Engineering / FX / FX Hub). Answer: yes, but scoped to **spot balance conversion**, not a full FX trading desk.

- **Client-facing (Studio v2)**: "FX Balance Currency Converter" widget. Entitlement `EMS_CAN_CONVERT_CURRENCIES` + `EMS_OPS_CAN_VIEW_FX`/`AMEND_FX`. Routes via `ems-fxall-gw` → FXall (LSEG) → LPs: Citi/HSBC (US, CST), BMO (Canada, CCA).
- **Internal (Studio v1)**: FX trade history view/amend for ops. Flag `studio.federation.fx.access` (old) → `studio.federation.fx-operations.access` (migration).
- **Live FX quotes widget + dedicated FX workspace** in `ems-ui`: FX-267 shipped to prod 2026-08-20 **behind a feature flag** (`studio.ems.live_fx.widget.access`). Not GA.
- **Prod footprint is tiny**: 3 client accounts (QLIQ, Scalebuilder, Talaria Crossover) + 2 house FX facilitation accounts. All "Relaxed" US rules, $10m daily entity limit. Markup 2–4bps client, 0 house.

## 21:35
Scanned cs-dev's HYPL mark price topic for `settl_price_type: final` records.

- Topic is `mktdata.mark_price.HYPL.PERP.BTC-USDC-USDC`, single partition, 5d retention.
- No network path to cs-dev Kafka from the laptop: the PULSEPRIME advertised listener
  (`kafka-broker-N.cs-dev.tokyo.pulseprime.systems:9093`) does not resolve locally, so
  `tools/kafka-capture` can't be used. Route that worked: `kubectl port-forward` to
  `pod/kafkarestproxy-0` in ns `confluent-cluster`, then the REST proxy v2 binary consumer API
  (assign + positions/beginning + drain `/records`). Scripts saved in
  `scratch/pulse/hypl-markprice/{drain.sh,decode.py}`.
- 8138 records total. Two shapes only: 8062 carrying
  (index_price, mark_price, funding_rate/theoretical), and 76 carrying a *lone*
  funding_rate/final entry. Final never travels with a mark price.
- 76 final entries = 24 distinct hourly settlements (2026-09-10 22:00 .. 2026-09-11 21:00 UTC),
  each republished 2-8 times. First copy lands 1-6s after the hour; stragglers repeat the same
  value up to ~50 min later (e.g. offset 466 at 23:49 still carrying the 23:00 value).
- `next_funding_time` is never populated on this topic - not on final, not on theoretical.
- 22:00 through 01:00 all read exactly 0.0000125 (HL's default 0.00125%/hr); real negative
  rates only start at 02:00. Looks like the feed served the venue default before it had data.

Gotcha worth remembering: `Decimal`'s CBOR mantissa is **little-endian** i128 with trailing
zero bytes trimmed (`libs/core/crates/message/src/types/decimal.rs:656`, deser pads to 16 and
`i128::from_le_bytes`). The schema doc says big-endian
(`types.yml:150`, `default_types.rs:159`) - that doc is wrong. Decoding BE gives plausible-
looking garbage for negatives (1e28-scale numbers), which is how I caught it.
