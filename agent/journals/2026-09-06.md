
## Deribit subscribe pacing

Deribit option feed handlers were logging sustained `too_many_requests (10028)` on
`public/subscribe` across 3 pods. Root cause: `ThrottledSubscriptionSender` queues *already
encoded* frames, so the one-instrument-at-a-time drip from refdata churn became one request per
instrument. Compounded by `SUBSCRIBE_REQUESTS_PER_SEC = 4` being a per-process global (5/s x 3
pods = 15/s) against Deribit's real `public/subscribe` ceiling of ~3.3/s per-IP.

Third defect, deferred: a rejected subscribe is popped from the queue and the symbol is already
in `subscribed`, so nothing retries and those instruments go dark silently. Eric's logs confirmed
the session survives the 10028 (no reconnects), so that hole is the live failure mode, not a
corner case.

Shipped Deribit-only: a coalescing pacer in the encoder slot (per-channel last-intent map,
flushed from the receive loop because the encoder slot has no idle tick), one request per 1250ms
via a shared per-process throttler, a reconnect quiet period, 10028 backoff, and 10028 dropped
from error to warn. 3 files, +946/-29, 72 tests green, lint clean. Branch
`deribit-subscribe-pacing`, not pushed.

Broader plan for the no-holes/per-venue-configurable version written to
`repos/pulse/.claude/plans/mktdata-subscription-pacing.md` — 6 PRs, covers all four subscription
paths (32-venue shared-socket, per-symbol-socket, multi-sub, FIX). Eric wants that started this
week.

Two gotchas worth remembering: Deribit request ids are second-resolution and the error response
carries no id, so rejection->request correlation needs a schema change first; and
`ReconnectingWsClient` does not guarantee `Closed` precedes `Reconnected` (the ping-send path
swallows it), so state models must reset off `Reconnected`.
