## Voyager interest rate consumption — investigation results
Eric's suspicion confirmed: **FACT via Snowflake, daily batch, not streaming.**

Pipeline: `FACT.RATES.VW_BENCHMARK_RATES` (Snowflake) → `swaps-load-benchmark-rates-job` →
`market_data.benchmark_rate` (Postgres) → `swaps-market-data-service` REST →
`benchmark-rate-provider` → `BenchmarkRateContainer.getRate(code, businessDate)` → 7 services.

- Job: Spring Batch `DailyLoadJob`, cron `0 17 * * *` America/New_York, profile includes
  `fact-datasource`. Incremental watermark from processing-records (`BENCHMARK_RATES`).
  Config `source-system: FACT`, start-date 2024-03-26, batch 5000.
- Which rates load is data-driven off `BenchmarkDefinition` rows via
  `getBenchmarkDefinitionsForSystem("FACT")` — the extension seam. Definitions are time-versioned
  (validFrom/validTo) and carry a holiday calendar + `source_config_load_cut_off_time`.
- Seeded codes are broad + multi-currency, Bloomberg-style tickers: SOFR, EFFR, OBFR, FEDL01,
  GCFR, LIBU3M, ESTRON, EONA, EURI1M/3M/6M/12M, CDOR, BBSW, NIBO*, JIBA, etc. V0.1.12 flipped
  every definition to `source_config_system = 'FACT'` (an 'OBFR'/'BBG' row hints Bloomberg was the
  prior source system).
- Consumers: trade-store-processor (TradeDate/SettleDate interest handlers, InterestUtils, basket
  accrual projection + recap), transaction-ledger (InterestOnBalanceHandler), funding-attribution,
  data-aggregation (ExcessEquityCostPosting), regulatory-reporting (MiFID), order-management,
  frontend-gateway (SwapOrderController).

**CORRECTION to my earlier read of `voyager_benchmark_rate`.** I initially told Eric it looked like
a built-out Voyager-native rate ingestion path that Kafka could land into. It is not. Migration
V0.1.28 creates the table and seeds exactly ONE row: `VOYAGER_ZERO` (renamed `BENCHMARK_ZERO` in
V0.1.29), rate 0.0, dated 2020-01-01, source system `VOYAGER` — a synthetic zero-rate constant so
trades with no real benchmark can still reference a benchmark code. Nothing in Java writes it; only
3 files touch the entity (read path, repo, model). The repo does expose loading-shaped methods
(`deleteRates(businessDate)`, `getLastLoadedDate(code)`) that nothing calls.
Still architecturally useful: it proves the read path merges a second table on the same benchmark
codes, and `VOYAGER` already exists as a valid source system value. But it's a placeholder, not a feed.

**The real design risk for getting `mktdata.fundingrate` into Voyager**: the consumption model is
firmly daily-accrual term financing, not a rate stream. `InterestUtils` shows rate *fixing/reset*
machinery — `BenchmarkRateFixingConfig`, `ResetConfiguration`, `ResetCalendarItem`,
`getMinUnfixedRateDate`, `DEFAULT_LOOK_BACK_DAYS = 10`, `BusinessDateCalendar` for holidays — and
day-count accrual via `calculateDayCharge(amount, allInRate, dayCount)`. Benchmark codes are
resolved from pricing sheets (long interest / short interest / GC stock loan fee) with hierarchy
Trade override > Basket override > Pricing sheet. Perp funding is typically 8-hourly; `getRate(code,
businessDate)` has no room for intraday grain. That mismatch is the hard part, not the plumbing.

## 12:23
Eric asked whether the expired-option auto-delist handles scaleset removal. It did not.

Found the gap: `refdata-fetcher` auto-delists expired options purely as refdata deletes
(`RefDataDiffFinder` -> `RefDataDiffEncoder` -> listed refdata topic). It has no scaleset
dependency at all. The mktdata scaleset coordinator lives in the `admin` app. The manual
`DELETE /refdata/list/instruments/:id` path *does* revoke, but auto-delist never did, so every
expired option that had `market_data_enabled` left a permanent assignment on the mktdata
scaleset topic. Symptom: mktdata-feed-handler logs `error!("received ScaleEvent for {symbol},
which is not defined in refdata")` on every rebalance/restart, and the assignment set grows
without bound.

Fix went into `admin/src/options_underlying_reconciler.rs` (the reconciler already reads current
assignments each tick and owns the coordinator): added `select_orphaned` — assigned keys that
parse as an expired option and are absent from the listed refdata cache — folded into
`select_targets` under the same per-tick cap, revokes before enables. Made
`refdata::diff::option_expired_before` pub so the reconciler and the delist share one definition
of "expired".

Two design points worth remembering: (1) the revoke is gated on *absent from cache* so a
deployment with delisting disabled can't flap (revoke, then re-enable off the flag, forever);
(2) the expiry test is the safety net so a lagging/incomplete cache can never cost a live
instrument its feed. Also had to drop the `no listed underlyings -> early return` guard, since
orphans outlive the underlying they hung off — costs one Kafka assignment read per 300s tick in
deployments with no options.

Left alone (flagged to Eric, not fixed): the per-symbol mktdata Kafka topics created on enable
are never deleted on delist.
